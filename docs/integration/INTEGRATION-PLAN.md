# 사용자 MVP 통합 계획

상태: Project 2 실행 기준
목표: Designer Studio에서 배포한 탁상형 템플릿 한 개를 기존 사용자 MVP에서 선택하고, 학교 데이터와 학사일정을 적용해 미리보기·인쇄용 PDF·기존 주문 흐름까지 연결한다.

## 통합 원칙

1. 사용자 Workspace를 새로 만들지 않는다. 기존 사용자 MVP의 화면, 일정 입력·인식, PDF, 금액 산정 흐름을 활용한다.
2. Designer Studio는 템플릿 구조와 Binding의 정본이다.
3. 사용자 MVP는 학교 정보, 일정, 월별 콘텐츠와 사용자 편집 프로젝트의 정본이다.
4. Template Runtime은 Template과 Dataset을 해석하고 `ResolvedDocument`를 만든다.
5. 화면 미리보기와 인쇄 출력은 같은 `ResolvedDocument`를 입력으로 사용한다.
6. 우리학교인쇄는 회원, 상품, 견적, 주문, 결제, 제작, 배송을 계속 담당한다.
7. 통합을 위해 레거시 DB 필드를 새 계약에 그대로 복사하지 않는다. 차이는 Adapter에서 변환한다.

## 첫 번째 종단 시나리오

> 사용자가 기존 MVP에서 학교명·교표·학교 전경·학사일정을 입력한다. Designer Studio에서 배포한 기본 탁상형 템플릿 하나를 선택한다. MVP 데이터를 Runtime Dataset으로 변환해 12개월 달력을 생성하고, 화면 미리보기와 인쇄용 PDF를 만든다. 이후 기존 금액 산정과 우리학교인쇄 파일 전달 흐름으로 이어진다.

### 첫 통합에 포함

- 기본 탁상형 템플릿 1개
- 임의 시작월 기준 연속 12개월
- 학교명, 교표, 학교 전경
- 단일 일정과 구간 일정
- 월별 이미지
- 화면 미리보기
- 인쇄용 PDF
- 기존 금액 산정 흐름 유지
- 최종 파일 전달 경계 확인

### 첫 통합에서 제외

- 모든 템플릿·달력 유형 동시 지원
- 사용자 자유 레이아웃 편집 전면 통합
- 협업 편집과 버전 병합
- AI 자동 레이아웃
- Publishing Geometry Runtime 전면 재설계
- 운영 DB·인증·결제 구조 변경
- 우리학교인쇄 운영 서버 즉시 배포

## 시스템 연결 구조

```text
Designer Studio ── 배포 Template Package ──┐
                                           ├─ Template Runtime ─ ResolvedDocument ─ 미리보기/PDF
사용자 MVP ── MvpDatasetAdapter ─ Dataset ─┘

사용자 MVP ─ 상품·수량 ─ 금액 산정 ─ 주문 ─ 우리학교인쇄
                                      └── 최종 PDF 및 메타데이터
```

## 단계별 작업

### 0. 에디터 기준선 고정

목적은 통합 중 에디터의 기준이 계속 바뀌지 않게 하는 것이다.

- 최신 안정 커밋과 검증 결과 기록
- 차단 문제와 통합을 막는 중요 문제만 즉시 수정
- 글자·간격·편의 기능은 별도 개선 목록으로 관리
- 대표 탁상형 템플릿과 샘플 프로젝트 JSON 고정

완료 조건:

- 대표 템플릿을 저장하고 다시 불러올 수 있다.
- 시작월, 12개월, 앞·뒤면, 일정, 이미지 Binding이 유지된다.
- 전체 자동 검사가 통과한다.

### 1. 사용자 MVP 현황 분석

사용자 MVP 저장소를 받은 뒤 코드를 복사하기 전에 실제 경계를 확인한다.

- 실행·빌드·배포 방식
- 사용자 프로젝트 저장과 재열기 방식
- 학교 정보와 이미지 Asset 구조
- 일정 직접 입력, 워드·엑셀 인식, 공휴일·절기·음력 구조
- 월별 이미지·텍스트와 사용자 편집 구조
- 미리보기 및 PDF 생성 경로
- 상품·수량·페이지 수와 금액 산정 경로
- 최종 파일 업로드·주문 전달 경계
- 단일 템플릿 하드코딩 위치

산출물:

- 실제 MVP 필드가 채워진 `MVP-DATA-MAPPING.md`
- 재사용, 교체, 보류할 MVP 모듈 목록
- 첫 통합을 막는 항목 목록

### 2. 계약 고정

문서와 현재 구현 사이의 느슨한 부분을 대표 시나리오에 필요한 만큼만 강화한다.

- Template Package와 manifest 버전 확인
- Dataset의 학교, 달력, 일정, 월별 이미지 세부 필드 확정
- Asset 참조 방식 확정
- Binding 경로와 필수·선택 입력 확정
- Runtime 오류·경고 반환 방식 확정
- 프로젝트 저장 정보와 Runtime 입력의 경계 확정

수정 대상:

- `schemas/runtime/dataset-contract.schema.json`
- `packages/template-runtime/src/types.ts`
- 필요 시 Template Package의 `contracts/data-bindings.json` 생성 규칙

완료 조건:

- 대표 Dataset 예제가 Schema 검증을 통과한다.
- 잘못된 날짜, 누락 Binding, 없는 Asset을 구분해 보고한다.
- 계약과 TypeScript 타입이 같은 필드를 설명한다.

### 3. MVP Adapter 구현

기존 MVP 모델을 직접 바꾸기보다 `MvpDatasetAdapter`에서 Runtime Dataset으로 변환한다.

- 학교 정보 변환
- 이미지 업로드 결과를 Asset 참조로 변환
- 일정 날짜·구간·분류 정규화
- 시작월 기준 12개월 키 생성
- 월별 이미지 `YYYY-MM` 매핑
- 원본에 없는 기본값과 경고 기록
- Dataset Schema 검증

필수 자동 검사:

- 1월 시작과 중간월 시작
- 연도를 넘는 12개월
- 단일 일정과 여러 주에 걸친 구간 일정
- 같은 날짜 여러 일정
- 이미지 있음·없음·잘못된 참조
- 선택 필드 누락

### 4. 템플릿 선택과 Runtime 연결

- Designer Studio의 배포 템플릿 패키지 불러오기
- manifest·Template·Asset·Binding Contract 검증
- 사용자 MVP에서 템플릿 선택 정보 저장
- Adapter가 만든 Dataset과 Template을 Runtime에 전달
- 기존 단일 템플릿 하드코딩을 대표 템플릿 선택 경로로 교체
- Runtime 진단을 사용자 확인 메시지로 연결

완료 조건:

- MVP를 다시 열어도 선택 템플릿 ID·버전과 원본 데이터가 유지된다.
- 템플릿만 교체해도 학교 데이터와 일정은 보존된다.

### 5. 미리보기와 PDF 연결

- 화면 Renderer와 PDF Adapter가 `ResolvedDocument`를 사용하도록 연결
- 페이지 순서, 앞·뒤면, 크기, bleed, crop mark 확인
- 이미지 fitting과 폰트 결과 비교
- 미리보기와 PDF의 위치·줄바꿈·월력·일정 차이 기록

첫 단계에서는 기존 MVP PDF 생성기의 강점을 유지한다. 다만 별도 데이터 해석을 반복하지 않고 `ResolvedDocument`를 받는 Adapter 뒤에 둔다.

완료 조건:

- 화면과 PDF의 페이지 수·순서·콘텐츠가 일치한다.
- 인쇄 크기와 재단 여백이 템플릿 규격과 일치한다.
- 뒷면 안내용 워터마크 등 출력 제외 개체가 PDF에 나오지 않는다.

### 6. 금액·주문·파일 전달 연결

- 기존 MVP 금액 산정 입력과 결과 보존
- 템플릿의 실제 페이지 수·규격을 가격 입력과 대조
- 주문 확정 시 우리학교인쇄 서버가 금액을 재검증하는 경계 확인
- PDF 업로드, 체크섬, 페이지 수, 크기, bleed 메타데이터 전달
- 편집 재개·재출력 시 파일 버전 처리 확인

운영 API는 `PRINT-ORDER-INTEGRATION-DRAFT.md`를 그대로 구현하지 않는다. 실제 우리학교인쇄 API 담당자와 확인한 뒤 확정한다.

### 7. 종단 검증과 확대

대표 학교 데이터 한 세트로 입력부터 파일 전달 직전까지 점검한다.

- 새 프로젝트 생성
- 기존 프로젝트 재열기
- 템플릿 변경
- 일정 수정 후 재출력
- 월별 이미지 교체
- 가격 재계산
- PDF 재생성 및 파일 버전 확인

대표 탁상형이 통과한 뒤 두 번째 템플릿, 벽걸이형, 엽서형, 포스터형 순서로 확대한다.

## 역할별 책임

| 영역 | Designer Studio | 사용자 MVP | Template Runtime/Publishing | 우리학교인쇄 |
|---|---|---|---|---|
| 템플릿 제작·배포 | 담당 | 선택만 | 검증·해석 | 담당하지 않음 |
| 학교 정보·일정 입력 | 샘플만 | 담당 | 읽기만 | 사용자·학교 식별 |
| 사용자 프로젝트 저장 | 담당하지 않음 | 담당 | 담당하지 않음 | 필요 시 주문 연결 |
| 화면 미리보기 | 제작 중 QA | 사용자 흐름 제공 | 공통 결과 생성 | 담당하지 않음 |
| 인쇄용 PDF | 출력 규칙 정의 | 생성 요청 | 파일 생성 | 수신·인쇄소 전달 |
| 금액·주문·결제·배송 | 담당하지 않음 | 기존 화면 유지 | 페이지·파일 메타 제공 | 최종 책임 |

## 검증 자료

첫 통합을 시작할 때 다음 고정 자료를 준비한다.

- 대표 탁상형 Template Package 1개
- 학교 정보가 채워진 MVP 프로젝트 1개
- 교표·전경·월별 이미지 Asset
- 단일·중복·구간·연도 경계 일정이 포함된 학사일정
- 기존 MVP 화면 캡처 또는 미리보기 결과
- 기존 MVP 인쇄용 PDF
- 같은 입력으로 만든 Runtime 결과

이 자료는 이후 변경의 회귀 검사 기준으로 유지한다.

## 전체 완료 기준

- Designer Studio에서 배포한 템플릿을 사용자 MVP가 불러온다.
- 학교명, 교표, 전경, 월별 이미지가 지정 Binding에 들어간다.
- 시작월 기준 연속 12개월과 연도 전환이 정확하다.
- 단일 일정, 같은 날짜 여러 일정, 구간 일정이 표시된다.
- 템플릿 변경 후에도 사용자 원본 데이터가 보존된다.
- 화면과 PDF의 페이지·콘텐츠·배치가 허용 오차 안에서 일치한다.
- PDF의 크기, bleed, crop mark, 출력 제외 규칙이 지켜진다.
- 기존 금액 산정과 주문 흐름이 유지된다.
- 최종 파일과 메타데이터를 우리학교인쇄 경계에 전달할 수 있다.
- 운영 서버 배포 전 별도 통합 QA가 완료된다.
