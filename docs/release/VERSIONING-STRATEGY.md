# ACDL 버전 관리 정책

Updated: 2026-08-05

## 기준선

- **v1 기준 코드:** `main`의 커밋 `cceeb4d7d5ac351184d447d51a43ec72cba99b86`
- **보존 브랜치:** `release/v1.0.0-mvp`
- **후속 개발 브랜치:** `v2-development`
- **v2 최초 애플리케이션 버전:** `2.0.0-alpha.1`

`release/v1.0.0-mvp`는 v2 구조 개선 전의 동작 기준선입니다. 버그 재현과 결과 비교에 사용하며 신규 기능을 직접 개발하지 않습니다.

## 세 가지 버전

| 구분 | 예시 | 의미 |
|---|---|---|
| 애플리케이션 버전 | `2.0.0-alpha.1` | Studio, Workspace 및 통합 제품의 개발 상태 |
| Template Schema 버전 | `schemaVersion: 1` | 저장되는 Template JSON 구조 |
| Runtime 버전 | `runtimeVersion: 1` | 템플릿을 해석하고 그리는 실행 계약 |

애플리케이션의 메이저 버전과 Schema·Runtime 버전은 독립적으로 관리합니다. v2 개발 시작만으로 Schema나 Runtime 버전을 임의로 올리지 않습니다. 실제 계약 변경과 마이그레이션이 추가될 때만 각각 변경합니다.

## v2 목표

실제 학사달력 샘플 5~6개를 비교 분석하고 대표 템플릿을 순차 구현하여, 다양한 디자인을 안정적으로 제작·사용·출력할 수 있는 공통 에디터 구조를 확립합니다.

- 실전 샘플 기능 매트릭스
- 공통 Template Schema와 마이그레이션 정책
- Studio·Workspace·미리보기·출력의 공통 Runtime
- Inspector의 콘텐츠·디자인·배치·동작 구조
- 자산 라이브러리와 개체 속성 편집 분리
- 템플릿 이름 분기 대신 capabilities 기반 동작
- 대표 샘플 기반 자동 회귀 테스트
- 사진 프레임·콜라주·월별 테마 등 검증된 신규 기능

## 버전 진행 규칙

| 단계 | 버전 예시 | 진입 기준 |
|---|---|---|
| 기준선 | `v1.0.0-mvp` | v2 구조 개선 직전 코드 보존 |
| Alpha | `v2.0.0-alpha.1` | 샘플 분석 및 구조 개선 진행 |
| Alpha 체크포인트 | `alpha.2`, `alpha.3` | 대표 샘플 또는 공통 구조 단위 검증 |
| Beta | `v2.0.0-beta.1` | 주요 기능 통합 후 전체 회귀 테스트 |
| Stable | `v2.0.0` | 실제 템플릿 제작 기준으로 안정화 |

## 브랜치 운영

- `main`: 현재 안정 기준 및 검토 완료 변경
- `release/v1.0.0-mvp`: v1 읽기 전용 기준선
- `v2-development`: v2 Alpha 통합 개발
- 기능 작업은 별도 브랜치에서 진행하고 검증 후 `v2-development`에 합칩니다.
- v2가 안정화되기 전에는 `main`의 v1 동작을 깨는 변경을 직접 반영하지 않습니다.

## 호환성 원칙

1. 기존 Template JSON을 버리지 않습니다.
2. Schema 변경에는 명시적인 마이그레이션 함수와 회귀 테스트를 함께 추가합니다.
3. Studio에서 저장한 결과는 Workspace, 미리보기, 출력에서 같은 Runtime 계약으로 해석합니다.
4. 템플릿별 예외보다 capabilities 선언을 우선합니다.
5. 대표 샘플은 신규 기능 발굴 자료이자 회귀 테스트 fixture로 관리합니다.

## v2 첫 작업

1. 샘플 5~6개 동일 기준 비교 분석
2. 개체·자산·데이터·스타일 기능 매트릭스 작성
3. 공통 Schema/Runtime과 중복 렌더링 경로 감사
4. Inspector 및 자산 관리 정보 구조 확정
5. 대표 템플릿 선정 후 하나씩 구현
