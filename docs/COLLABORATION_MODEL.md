# 협업 모델 (계약 우선 / Contract-First)

이 문서는 **팀원과 개발자가 함께 서비스를 만드는 방식**의 기준입니다. AI는 새 프로젝트나 새 기능을 시작할 때 이 모델을 따라 팀원을 유도하고, 개발자에게 넘길 것과 넘기지 않을 것을 이 기준으로 나눕니다.

팀원과 개발자를 나누는 선은 "누가 엔지니어냐"가 아니라 **"위험이냐 아니냐"**입니다. 계약(데이터 모양) 앞쪽은 누가 하든 AI와 함께 만들 수 있고, 계약 뒤쪽(운영 API·운영 DB·인증·결제·외부 연동)은 개발자가 소유합니다.

## 핵심 아이디어

팀원과 개발자는 서로의 **작업을 합치지 않습니다.** 처음에 **규격(계약, 데이터 모양)만 맞추고 각자 따로 만든 뒤**, 마지막에 목(가짜)을 진짜로 바꿉니다.

- **계약(contract)** = 주소(`/api/*`)와 데이터 모양. `src/lib/api/contracts.ts`에 타입으로 둔다.
- **껍데기 vs 알맹이** — API는 두 겹이다.
  - 껍데기(계약) = 주소 + 데이터 모양. 처음에 합의하고 고정한다.
  - 알맹이(구현) = `/api/*` 내부 저장소 구현. 개발/검토 단계에서는 Supabase Postgres를 쓰고, 운영 전환 시 개발자가 운영 API·운영 DB로 교체한다.
- 계약(껍데기)만 고정되면, 저장소 구현을 바꿔도 **화면은 깨지지 않는다.**

## 왜 "계약 우선"인가 (A도 B도 아님)

- **A. 개발자가 착수 전에 전체 설계를 잡아주기** → 매 프로젝트마다 설계 회의가 필요해 개발자가 병목이 되고, 화면도 보기 전에 구조를 정하니 자주 틀린다.
- **B. 팀원이 다 만든 뒤 개발자가 받아서 역해석·정리** → 남이 만든 실기능 코드를 사후에 리버스엔지니어링하는 통합 지옥.
- **정답. 계약 우선** → 개발자는 착수 시점에 **계약만** 확인하고(작고 대개 비동기), 팀원과 개발자가 **동시에** 각자 만든다. 완성되면 목을 진짜로 교체.

## 흐름 (5단계)

1. **기획 (팀원 + AI)** — AI가 질문형 브레인스토밍으로 요구를 끌어낸다. 산출물: 스펙 + **데이터 모양(계약) 초안** + **위험/개발자 확인 목록**. 자세한 절차는 `docs/PLANNING_ELICITATION.md`.
2. **계약 확인 (개발자)** — 개발자는 전체 설계가 아니라 **계약(데이터 모양)과 위험 목록만** 본다. "이 모양 맞죠? 지금 내가 가져갈 건? 나중에 할 건?" → 대개 채팅으로 승인, **새롭거나 위험한 프로젝트일 때만 짧은 회의.**
3. **병렬 작업 (동시에)**
   - 팀원 + AI: `/api/*` route + 화면·기능 (계약 앞쪽). 데이터가 남아야 하면 개발/검토용 Supabase Postgres로 실제 저장까지 만들고(최소), 그 외에는 목(가짜 데이터)으로 둔다.
   - 개발자: **운영 API + 운영 DB(진짜 알맹이)** (계약 뒤쪽). 팀원 화면을 기다리지 않는다.
4. **스위치 (개발자)** — 백엔드가 준비되면 `docs/API_CONTRACT.md`에 진짜 주소·명세를 채운다. 이것이 "이제 목을 진짜로 바꿔도 됨" 신호다. 목 route를 실제 연동으로 교체한다. **화면(프론트)은 바뀌지 않는다.**
5. **사용자 공개 반영 (개발자)** — 개발자가 최종 확인 후 별도 릴리스 절차로 실제 서비스에 반영한다.

## 개발자가 손대는 지점은 딱 두 번

- ② **계약 확인** (대개 채팅)
- ④ **스위치** (백엔드 완성 후 교체)

그 사이에는 개발자가 불려가지 않는다. 이것이 개발자 부담(병목)을 없애는 핵심이다.

## API 문서는 결과물이 아니라 출발점

개발자가 백엔드를 다 만든 뒤 API 문서를 만들어 팀원에게 넘기는 방식(옛날 방식)이 아니다.

- 처음에 합의한 **계약(데이터 모양)이 곧 API 문서** 역할을 한다. 팀원은 이 계약을 보고 이미 화면을 만든다.
- 개발자는 **새 API를 설계해 넘기는 게 아니라, 이미 약속된 계약을 진짜로 지키게** 운영 API·운영 DB를 만든다.
- 완성되면 `docs/API_CONTRACT.md`에 실제 주소·명세를 채워 목→진짜 전환을 연다.

## A↔B는 고정이 아니라 다이얼

- **새로움·위험이 높으면** → 계약 합의를 앞에서 (짧은 회의, A쪽).
- **루틴·저위험이면** → 자율 진행 + 계약 비동기 승인 (B쪽).

팀과 패턴이 익을수록 다이얼은 B쪽으로 이동한다. 협업 방식이 애매한 것이 아니라, 프로젝트의 새로움에 따라 슬라이드하는 하나의 축이다.

## AI가 지켜야 하는 것

- 데이터를 표시하는 기능은 계약(`src/lib/api/contracts.ts`) + `/api/*` 목 route 뒤에서 만든다. 컴포넌트에 인라인 목 배열을 두지 않는다. (자세한 규칙은 `AI_START_HERE.md`의 데이터 표시 규칙.)
- 계약 뒤쪽(운영 DB·인증·권한·결제·개인정보·외부 API·사용자 공개 반영)은 팀원이 확정하지 않는다. 개발/검토용 Supabase 저장은 계약 앞쪽이라 필요하면 만든다. 운영 전환·위험 항목은 `HANDOFF.md`의 개발자 이관 목록에 **모아서** 기록한다.
- 새 팀원용 커맨드를 만들지 않는다. 기획 브레인스토밍과 계약 생성은 공식 커맨드 6개 밖의 **내부 절차**로 진행한다.
