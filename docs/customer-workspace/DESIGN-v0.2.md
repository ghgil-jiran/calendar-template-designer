# 신규 달력 사용자 서비스 설계서

버전: v0.2 / 작성일: 2026-11-07

상태: 사용자 합의사항을 정리한 설계 초안. 코드 의존성·연동 규격 조사는 미실시이며, 아래 제안은 해당 조사 후 확정한다. 구현·배포·백업 완료 보고가 아니다.

## 1. 목적과 기본 원칙

사용자가 완성도 높은 템플릿을 선택하고 필수 자료를 입력한 뒤, 최소 편집과 전체 페이지 확인을 거쳐 최종 작업본을 기존 주문 시스템에 전달한다. 초기 출시는 학사달력·탁상달력에 한정한다. 이후 다른 달력 유형을 수용할 수 있는 구조로 설계한다.

신규 서비스는 템플릿을 서비스 전용 모델로 재해석해 별도 렌더링하지 않는다. 템플릿 에디터의 실제 개체·렌더링·편집 엔진을 공통화해 사용한다. 관리자용·사용자용 인터페이스는 구분한다. 엔진 코드를 복사해 두 구현으로 발전시키지 않는다.

새 템플릿 또는 스타일을 제공할 때 사용자 서비스의 렌더링을 다시 구현하지 않는 것을 핵심 합격 기준으로 삼는다. 엔진 버전 갱신·배포와 새 입력 기능 추가는 필요할 수 있다.

## 2. 사용자 흐름

### 2.1 템플릿 선택·자료 입력

첫 페이지에서 게시된 템플릿과 내 프로젝트를 제공한다. 실제 디자인의 표지·대표 내지·전체 미리보기 및 필요한 자료를 안내한다. 선택 후 학교 정보·학사일정·사진 입력으로 이어진다. 한 화면에 모든 입력을 처음부터 펼치는 대신 진행 상태에 따라 보여주는 구성을 제안한다. 최종 화면 구성은 검토 대상이다.

학교 정보는 템플릿에 설정된 필수·선택 항목을 한 번에 폼으로 입력한다. ‘달력에 표시하지 않음’을 선택한 값은 연결 개체에서 제외한다. 숨김에 따라 주변 개체를 자동 재배치할지는 별도 확정한다. 임의로 디자인을 재구성하지 않는다.

학사일정은 Word·Excel·TXT 등 파일을 일괄 업로드하고 추출 내용을 사용자가 확인한다. 간단한 표 편집으로 날짜·기간·일정명 수정, 추가·삭제를 제공하는 방향이다. 모호한 날짜·연도와 해석 실패는 사용자 확인 대상으로 남긴다. 구체적인 확장자와 추출 방식은 미확정이다.

사진은 일괄 업로드하고 사용자 사진 라이브러리에 보관한다. 편집 화면에서 해당 페이지의 교체 가능한 프레임에 적용한다. 업로드 시 품질 경고를 제공한다. 프레임 배정 전에는 원본 크기 기준의 예비 안내이며, 실제 배치 DPI는 적용·확대 후 계산한다.

미입력에는 템플릿 샘플값을 기본 표시하되, 사용자가 제외하면 표시하지 않는다. 템플릿에서 필수 교체로 지정한 항목은 반드시 사용자 값으로 교체한다. 필수 입력·필수 교체·표시 제외 간 우선순위는 최종 확정이 필요하다.

각 단계는 저장 후 다음으로 이동한다. 서버 저장을 기준으로 로컬 임시 캐시를 복구 보조로 사용하는 것을 제안한다. 로컬 캐시만으로 사진·프로젝트·최종본을 보존하지 않는다. 저장 실패 시 입력을 유지하고 다음 단계 완료로 처리하지 않는다.

### 2.2 내 달력 확인·최소 편집

공통 엔진으로 전체 페이지를 표시하고 페이지 목록·이전/다음·확대를 제공한다. 교체 허용 프레임의 사진 교체 및 프레임 안 사진 이동·확대/축소만 제공한다. 프레임 자체 이동·크기 변경, 사진 회전, 자유 텍스트 추가, 월력 스타일 변경은 초기 제공하지 않는다.

학교 정보 등은 직접 캔버스에서 수정하지 않고 ‘기본 정보 수정’ 메뉴로 입력 화면에 돌아가 수정한다. 기존 사진 배정·자르기 등 관련 없는 편집값은 유지한다. 학사일정 수정도 입력 편집으로 연결한다.

최종본 미리보기는 팝업에서 페이지를 넘기는 방식으로 사용자에게 제공한다. 모양 확인용 PDF 다운로드는 관리자 기능으로 유지한다. 사용자 미리보기와 편집 화면은 동일 프로젝트 버전·엔진으로 표시한다.

### 2.3 최종 완료·주문 전달

최종 저장·주문 단계에서 필수 항목과 배치 사진 품질을 다시 확인한다. 사진 품질 부족은 사용자에게 알리고 수정 또는 확인 후 진행을 허용한다. 최소 DPI는 템플릿의 인쇄 기준을 사용하되 구체적인 하향 조정값은 별도 결정한다. 기존 템플릿의 값을 임의로 변경하지 않는다.

확인한 최종 작업본을 고정해 저장하고 기존 주문 시스템에 전달한 뒤 이동한다. 최종 작업본에는 템플릿 버전·학교 정보·일정·사용 자산 참조·사진 편집값·엔진 버전 등 재생성에 필요한 정보가 포함돼야 한다.

서버는 확정본을 기준으로 인쇄 PDF를 생성·검증한다. 사용자에게 생성 완료까지 대기를 요구하지 않는 방향을 제안한다. 기존 주문 시스템이 받을 확정본 파일/참조와 이후 인쇄 PDF의 연결 계약은 별도 확인한다.

수량·가격·배송·결제·최종 주문·접수 이후 상태·운영자 보완은 기존 시스템의 영역이다. 신규 서비스에는 주문 관리 화면을 만들지 않는다. 신규 서비스는 작업본 저장·전달 실패 안내와 재시도를 제공한다. 주문 중복 등 업무 처리는 기존 시스템에서 담당한다. 재시도 시 같은 확정본 식별자를 재사용해 전달 결과를 구분할 수 있게 한다.

## 3. 프로젝트와 인증

기존 시스템의 ‘달력 직접 만들기’에서 로그인 후 진입한다. 초기 주문 정보 없이 사용자 ID·이름 등 식별 정보를 전달받는다. 서버가 신뢰할 수 있는 인증 전달 방식과 작업 소유권 검증이 필요하다. URL에 적힌 ID만 믿는 방식은 사용하지 않는다. 구체적 인증 연동은 미확정이다.

내 프로젝트에서 작업 중·저장된 프로젝트를 확인하고 다시 연다. 초기에는 프로젝트 안의 템플릿 변경을 제공하지 않는다. 저장된 프로젝트를 복사해 새 프로젝트로 시작할 수 있게 한다. 최종 완료 후 재편집은 허용하되 주문 전달된 확정본은 보존하고 새 작업 버전으로 수정한다.

## 4. GitHub·프로그램 구성 제안

템플릿 에디터 저장소 ghgil-jiran/calendar-template-designer를 기반으로 디자이너 앱·신규 사용자 앱·공통 엔진·공통 데이터 정의·출력 Worker를 한 저장소에서 관리하는 모노레포를 제안한다. 실제 폴더 배치와 이전 범위는 최신 원격 코드 조사 후 확정한다.

| 구성 | 책임 |
|---|---|
| 디자이너 앱 | 유형·템플릿 제작, 자산 관리, 게시 |
| 신규 사용자 앱 | 선택·자료 입력·최소 편집·저장·최종본 전달 |
| 공통 엔진 | 원본 개체·스타일 표시, 데이터 연결, 편집, 출력 화면 |
| 공통 데이터 정의 | 템플릿·프로젝트·권한·자산·버전 |
| 출력 Worker | 인쇄 PDF 생성·원본 배경 합성·검증 |

기존 사용자 서비스의 전용 변환 모델과 별도 React 달력 렌더러는 신규 구조의 기반으로 삼지 않는다. 날짜 계산·자산·권한·일정 처리 등 유용한 기능은 의존성을 검토해 선별 재사용한다.

엔진 변경은 디자이너 앱과 사용자 앱이 같은 소스로 사용한다. 템플릿의 엔진 요구 버전과 고객 앱 지원 버전을 확인하고 지원 엔진 배포 후 새 템플릿을 공개한다. 기존 프로젝트·확정본은 템플릿 버전을 고정한다. 장기 재현을 위한 엔진 버전 보존 방식은 추가 설계한다.

## 5. 서버 운영 제안

코드는 한 저장소에서 관리하되 사용자 웹서비스·디자이너 웹서비스·출력 Worker는 배포와 권한을 구분한다. 처음부터 별도 물리 서버 세 대가 필요한 것은 아니다. 데이터·자산 저장소는 권한을 구분해 사용한다.

사용자 서비스는 관리자 사이트의 하위 화면이나 관리자 로그인 세션에 의존하지 않는다. 디자이너 사이트를 점검해도 고객은 게시된 템플릿으로 작업할 수 있어야 한다. 고객용 배포에 같은 엔진을 포함하며 관리자 화면을 매번 호출해 그리지 않는다. 긴 PDF 작업은 웹 요청과 분리한다.

## 6. 기존 사용자 서비스 동결·백업

대상 저장소: ghgil-jiran/-v1.1. 기존 서비스는 앞으로 기능 수정 없이 보존하고 신규 구현의 참고·추출 원본으로 사용한다. 이 문서는 동결 방침을 기록한 것이며 현재 원격 상태·배포 변경이나 백업을 수행한 것은 아니다.

### 6.1 지금 확보할 기준점

후일 전체 백업만 하는 것에 앞서, 최초 보존 작업에서 원격 최신 브랜치·커밋·배포 버전·동작에 필요한 구성 목록을 기록하고 변경되지 않는 보존 태그 또는 백업 참조를 확보한다. 로컬 미커밋 파일과 로컬 전용 설정·Worker 산출물의 존재도 확인한다. 실제 작업은 별도 실행하며 일반 개발 변경을 섞지 않는다.

### 6.2 전체 백업 시점과 범위

인쇄 기능 이전과 신규 서비스의 해당 기능 검증을 마친 뒤, 기존 배포·계정·저장소를 종료하거나 보관 처리하기 전에 전체 백업과 복원 확인을 완료한다. GitHub 소스만으로 전체 백업이 되지는 않는다.

| 범위 | 보존 내용 |
|---|---|
| 소스 | Git 이력·브랜치·태그, 잠금 파일, 별도 패키지·LFS가 있다면 해당 원본 |
| 데이터 | 사용자 프로젝트·템플릿·작업·인쇄 검사 기록, DB 스키마·정책·마이그레이션 |
| 자산 | 이미지·폰트·원본 배경 PDF·필요한 최종 결과물과 참조 관계 |
| 실행 환경 | 배포 설정, 환경변수 목록·보호된 실제 값, Worker 실행 조건 |
| 인쇄 도구 | Ghostscript·Inkscape·qpdf 등 사용 버전, ICC 프로파일, 실행 옵션 |
| 운영 문서 | 실행·복원 절차, 외부 연결, 백업 목록·체크섬 |

비밀값과 사용자 사진·템플릿 데이터를 소스 저장소에 업로드하지 않는다. 공유 인프라를 정리할 때 템플릿 에디터·신규 서비스가 함께 사용하는 DB·자산을 삭제하지 않는다. 저장소 archive, 배포 종료, 유료 자원 해제, 데이터 삭제는 별도 결정이다.

### 6.3 인쇄 품질 검사 이전

기존 구현을 기준 커밋에서 복사해 신규 공통 출력 영역으로 가져온다. 복사 후에는 신규 구현을 유지보수 기준으로 삼고 기존 서비스를 계속 맞추지 않는다.

Worker 파일만 가져오지 않고 잡 생성·큐/상태·인증·최종본 접근·업로드·재개 체크포인트·원본 PDF 합성·재단 표시·CMYK/K100·서체·검사·보고서·다운로드까지 의존성을 조사한다. 엔진 연결은 서비스 전용 렌더러 대신 에디터 공통 출력 경로로 바꾼다.

기존 성공 기록이 신규 경로의 검증 완료를 뜻하지 않는다. 이관 후 실제 PDF 생성·검사, 원본 배경 보존, 오류·재시도, 샘플 전체 페이지를 다시 확인한다. 출력 기능을 완전히 이전한 뒤 기존 코드의 참조를 종료한다.

## 7. 구현 순서

1. 최신 원격 확인, 기존 서비스 보존 기준점 확보, 엔진·기존 기능 의존성 조사.
2. 설계 미결정 항목과 첫 페이지·자료 입력 화면 확정.
3. 신규 앱 첫 페이지·내 프로젝트·자료 입력·단계별 저장 구현. 동시에 공통 엔진에 실제 입력 데이터를 전달하는 최소 연결 확인.
4. 동일 샘플 A 저장본으로 28면 표시, 정보·일정·사진 반영, 저장·재열기 검증.
5. 사진 최소 편집·사용자 미리보기·관리자 모양 PDF 구현.
6. 확정본·주문 전달·인쇄 검사 기능 이전과 서버 처리 검증.
7. A/B/C 전체 흐름 및 다른 규격으로 확장성 확인. 실제 인쇄·운영 환경 검증 후 출시 판단.

기존 서비스·신규 서비스·템플릿 에디터가 개발 중 공존하고, 전환 후 신규 서비스·템플릿 에디터를 운영한다. 기존 서비스의 백업은 재전환을 쉽게 보장한다는 의미가 아니다.

## 8. 완료 기준

- 같은 템플릿·데이터·엔진 버전에서 디자이너/사용자 화면의 개체·배치·스타일이 일치한다.
- 새 스타일·템플릿 추가에 사용자 전용 렌더링 수정이 필요하지 않다.
- 입력 제외·필수 교체·학사일정·사진 배정이 저장·재열기 후 유지된다.
- 사진만 허용 범위에서 편집되고 서버에서도 소유권·변경 권한을 검증한다.
- 사용자가 본 버전과 전달된 확정본·서버 인쇄 대상이 같다.
- 원본 배경 PDF 연결을 유지하고 최종 인쇄 PDF의 보존·품질을 별도 검증한다.
- 테스트 통과 / 배포 READY / 실제 화면 동작 / PDF 자동 검사 / 실제 인쇄 결과를 구분한다.
