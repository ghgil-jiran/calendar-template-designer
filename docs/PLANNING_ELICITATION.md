# 기획 끌어내기 (요구사항 브레인스토밍)

이 문서는 AI가 **새 프로젝트나 새 기능을 시작할 때** 팀원에게서 요구사항을 끌어내는 내부 절차입니다. 팀원이 스스로 완성된 스펙을 주지 못해도, AI가 질문으로 기획을 함께 만들고 그 결과를 **계약(데이터 모양)과 개발자 이관 목록**으로 정리합니다.

팀원이 새 화면/기능을 요청하면 AI가 바로 만들기 전에 이 질문 절차를 먼저 시작합니다. 팀원이 `기획해줘` 또는 `/schoolp-brainstorm`으로 직접 부를 수도 있습니다(스킬로 등록됨: Claude Code `.claude/skills/schoolp-brainstorm`, Codex `.agents/skills/schoolp-brainstorm`).

## 절대 규칙 — 하드 게이트

이 절차는 **질문을 하는 절차이지, 만드는 절차가 아니다.** 다음을 반드시 지킨다.

1. **요구사항이 확정되기 전에는 아무것도 만들지 않는다.** 스펙·`contracts.ts` 계약·코드·파일 생성 전부 금지. 질문 없이 곧장 계획서나 구현으로 넘어가는 것이 가장 흔한 실패다.
2. **한 번에 질문 하나만.** 여러 질문을 한꺼번에 나열하지 않는다. 하나 묻고 → 답을 받고 → 다음 하나.
3. **답이 모호하면 넘어가지 않고 보기를 제시해 확정될 때까지 되묻는다**("A인가요, B인가요?" 식).
4. **팀원이 놓쳤거나 서로 모순되는 가정은 그냥 받아 적지 않고 짚어서 되묻는다.**
5. 아래 "놓치기 쉬운 것"까지 다 채워졌다고 판단되면, **"이제 정리해도 될까요?"로 한 번 확인한 뒤에만** 산출물을 만든다.

Codex·Claude Code 모두 동일하게 적용한다. 특히 바로 실행하려는 편향이 강한 도구일수록 이 게이트를 먼저 지킨다. (기획문서가 이미 있는 경우는 아래 "이미 기획문서가 있으면"을 먼저 따르되, 게이트 1(확정 전 구현 금지)은 그대로 적용한다.)

## 언제 실행하나

- 새 프로젝트를 시작할 때
- 새 화면 또는 새 기능을 요청받았을 때
- 요청이 짧거나 모호해서 데이터/화면 범위가 불분명할 때

간단한 문구 수정, 스타일 조정처럼 데이터·기능이 없는 요청에는 실행하지 않습니다.

## 요청이 너무 크면 먼저 쪼갠다

요청이 여러 독립 서비스·화면 묶음("플랫폼 통째로", "챗봇이랑 주문관리랑 디자인허브 다")이면, 세부를 묻기 전에 **먼저 이 사실을 짚고 조각으로 나눕니다.**

- 독립적으로 만들 수 있는 조각이 무엇인지, 서로 어떤 관계인지, 어떤 순서로 만들지 함께 정합니다.
- 그중 **하나를 골라** 그 조각만 아래 질문 절차로 기획합니다. 나머지는 다음 차례로 둡니다.
- 거대한 걸 한 번에 삼키려 하지 않습니다. 조각마다 스펙 → 계약 → 구현을 따로 돕니다.

## 이미 기획문서가 있으면 (먼저 확인)

프로젝트에 기획문서(md 등)나 만들다 만 화면이 있으면, **백지에서 질문하지 않습니다.**

1. 그 문서/화면을 **먼저 읽고** 기획의 기준(plan of record)으로 삼습니다.
2. 이미 문서에 정해진 것은 다시 묻지 않습니다. 문서에 **없거나·모호하거나·서로 안 맞는** 부분, 그리고 아래 "놓치기 쉬운 것"만 확인합니다.
3. 만들다 만 화면은 보존하고 그 기획에 연결합니다.
4. 확인이 끝나면 아래 "산출물 3가지"(스펙·계약 초안·개발자 이관 목록)로 정리해 곧바로 이어서 구현합니다.

이런 자료가 전혀 없을 때만 아래 질문 절차를 처음부터 진행합니다.

## 질문 방식

엔지니어에게 묻듯 아키텍처를 묻지 않습니다. **서비스 언어로** 묻습니다.

- 무슨 서비스인지, 누가 쓰는지
- 핵심 화면은 무엇인지, 각 화면에서 무엇을 보고 무엇을 하는지
- 각 화면에 어떤 데이터가 필요한지 (목록/상세/입력)

**한 번에 질문 하나만** 합니다. 여러 개를 한꺼번에 나열하지 않고, 하나 묻고 답을 받은 뒤 다음 하나로 넘어갑니다.

## 놓치기 쉬운 것 캐내기 (핵심)

팀원이 스스로는 떠올리지 못하는 것을 AI가 대신 물어 표면으로 끌어올립니다.

- 데이터가 없을 때 화면은 어떻게 보이나 (빈 상태)
- 오류가 났을 때는 어떻게 보이나
- 이 데이터를 누가 볼 권한이 있나
- 저장/수정/삭제가 필요한가
- 검색·필터·정렬·페이지네이션이 필요한가
- 개인정보·결제·인증과 닿는 부분이 있나

여기서 "저장/수정/삭제·목록이 남아야 함"이 나오면 **개발/검토용 Supabase Postgres로 실제 동작하게** 만듭니다(계약에 묶어 최소로 — `docs/SUPABASE_WORKFLOW.md`). 운영 전환만 개발자 이관 목록에 남깁니다.

추가로 아래를 구분합니다.

- 파일 업로드가 있으면 Supabase Storage 필요 여부를 확인합니다.
- 여러 사용자가 같은 화면의 변경사항을 즉시 봐야 하면 Supabase Realtime 필요 여부를 확인합니다.
- 로그인 상태가 필요하면 schoolp member API 연동인지, 로컬 개발/검토용 임시 인증인지 구분합니다.

"권한", "결제", "개인정보", "실제 외부 연동" 같은 답은 **위험 신호**이며 개발자 이관 목록으로 분류합니다.

## 질문이 끝나면 — 접근안 2~3개를 먼저 제시

질문이 다 채워졌다고 곧장 스펙으로 가지 않습니다. **"이렇게 만들 수 있어요"를 2~3개 제시하고 하나를 추천**합니다.

- 각 안이 무엇이 다른지(범위·화면 구성·단계)를 **서비스 언어로** 쉽게 설명합니다. 기술 용어로 비교하지 않습니다.
- **추천안을 먼저 말하고 이유를 붙입니다**("저는 B를 추천해요 — 이유는…"). 팀원이 고르거나 섞을 수 있게 합니다.
- 팀원이 고른 뒤에만 아래 산출물로 넘어갑니다.

## 산출물 (반드시 3가지)

브레인스토밍이 대화로만 끝나면 안 됩니다. 접근안이 선택된 뒤, 아래 3가지를 만들어 냅니다.

1. **짧은 스펙** — 서비스/화면/기능 요약. `WORK_LOG.md` 또는 기획 노트에 정리.
2. **데이터 모양 초안 (계약)** — 화면에 필요한 데이터 타입을 `src/lib/api/contracts.ts`에 초안으로 만든다. 이 계약이 팀원 화면과 개발자 백엔드가 공유할 규격이 된다.
3. **개발자 이관 목록** — 위에서 나온 위험/확인 항목을 `HANDOFF.md`의 개발자 이관 목록에 **모아서** 기록한다. (작업 중간에 여러 번 멈추지 않고, 배치로 쌓는다.)

**만든 스펙은 넘기기 전에 한 번 자가검토합니다:** 빈칸(TBD)·서로 모순되는 부분·두 가지로 읽히는 모호한 항목이 없는지, 범위가 한 번에 만들기엔 너무 크지 않은지 훑고, 걸리는 게 있으면 바로 고치거나 팀원에게 한 줄로 확인합니다.

구현으로 넘어간 뒤에도 **요청한 범위만** 만듭니다(과잉개발 방지). 안 시킨 기능·리팩터·추상화는 얹지 않되, 화면이 제대로 돌아가는 빈/로딩/오류 상태와 명백한 버그 수정 같은 완성도는 줄이지 않습니다. 자세한 기준은 `AI_START_HERE.md`의 "범위 규율 (과잉개발 방지)".

## 계약 확인으로 이어가기

산출물이 나오면 `docs/COLLABORATION_MODEL.md`의 흐름을 따른다.

- 데이터 모양(계약)은 AI가 초안하고, **개발자가 확인/승인**한다. (대개 채팅, 새롭거나 위험하면 짧은 회의.)
- 승인된 계약 위에서 팀원은 `/api/*` 목 route + 화면을, 개발자는 백엔드 + DB를 **동시에** 만든다.

## 하지 말 것

- 팀원에게 아키텍처·기술 선택을 묻지 않는다 (상태관리, DB 종류, 프레임워크 등).
- 공식 API 문서가 없는데 실제 endpoint/field/status를 확정하지 않는다. 대신 타입이 붙은 `/api/*` 목 route를 만든다.
- 브레인스토밍 결과를 계약·이관 목록으로 정리하지 않고 곧바로 대량 구현으로 넘어가지 않는다.
